# project-handoff

## 指导思想

没写到的情况从这里推，两件正当的事冲突时按这里选。

- 成事优先。组织项目只为把事做成。一项维护值不值得做，看它能否让事做得更快、更准；挤占了做事的精力，就是本末倒置。
- 随时可接。项目要始终让零记忆的接手者打开就能接着干。接续做得到不到位，看能否不翻历史就认清当下的真实处境；放任状态过期会把方向带偏，只顾堆砌过程是在逼后人考古。
- 沉淀宁缺毋滥。留下的认识会被后来者当真。一条认识值不值得留，看它是否经得起检验、且能垫高往后的工作；把猜测当结论会一路误导，把琐事当经验只会淹没重点。
- 规则从简。能靠判断做对的事，不用规则去捆。一条规则该不该在，看它拦的是不是单靠判断避不开的大错；遇事就立规打补丁，只会把一时的局限冻成长期的枷锁。

## 底线

怎么权衡都不越过。

- 项目自足。项目的记忆与约定归项目自身所有——上下文落在项目内，不寄存在特定 Agent 的私有记忆里，也不绑定或回引 `project-handoff`。

## 落点

- 根 `AGENTS.md`：项目入口，也是根目录里唯一的维护文件。写项目定位、模型猜不到又常用的环境事实、项目自己的指导思想与底线（有才写），以及 `.handoff/` 里的东西怎么读写、去哪找。只读它、没装 `project-handoff` 的 Agent，也要能把项目接着维护下去。
- 业务内容：按项目自身最合适的方式组织，领域成果留在这里。
- `.handoff/`：其余维护内容都收在这里——现状、历史、协作沉淀与规程、过程草稿、维护脚本，写给下一个接手的 Agent。
  - 现状原地改写，接手先读它；改写时留住已被证伪的路，免得后人重走。
  - 历史只追加，过程草稿用完即收；平时不通读，溯源时再查。
  - 没有入口指向的沉淀与规程，等于不存在。
- 退场：退出活跃视野的内容，往后可能还有价值的归档，确定不要的删除。
- 脚本：可选。只用标准库、归项目所有，只算和报告、不拦；没有脚本就按同样口径现算。

## 初始化与接入

先看清项目现状，再问用户的原始诉求与期望，以及各类内容分别怎样跟踪或隔离；据此给出建议，用户确认后落定。强烈建议用 Git，不用也行，只是放弃历史版本。

- 全跟踪：所有项目与维护内容全部入库，只排除构建缓存、运行产物与本机配置等杂项。
- 常规跟踪：业务、设计调研、`AGENTS.md` 与 `.handoff/` 入库，排除私密内容（如 `local`、`secret` 类）及构建与本机杂项。
- 只公开核心成果：仅业务与公开文档入库，`AGENTS.md`、`.handoff/` 与私密内容只留本机不跟踪。

不希望在仓库中暴露被排除项时，入库的 `.gitignore` 不点名私有路径，改用通配黑名单配显式白名单（如 `.*` 默认忽略点开头项，再以 `!.gitignore`、`!/.github/` 等放行需跟踪项），通配未覆盖的本机私有项（如 `/AGENTS.md`）写入纯本机的 `.git/info/exclude`；已跟踪的文件、注释与提交说明中不提及未跟踪内容。

## 规则

- 反复出错时，先看是不是状态源脏了、上位思路偏了，或者这个动作能用工具省掉；低代价的偶发错直接接受。都不是，才立规。
- 复发只是“单靠判断避不开”的线索，本身不是立规的理由；高危红线来自用户的真实环境，由用户给出；环境事实是记忆，不受这把尺子卡。
- 不用数字规定文档形态和维护动作：数字一成目标就会被绕过，还会把当下模型的局限冻住。
- 写项目自己的指导思想与底线时，每条亮出取舍的尺子、点名聪明人也容易掉进去的陷阱；反面没人会选的话不写，没有真实禁区就不立底线。
